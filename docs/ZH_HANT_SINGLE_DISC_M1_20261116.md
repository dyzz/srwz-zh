## 1. 做了什么

| 部分 | 实现 |
| --- | --- |
| 两份可执行文件 | **简体** = v0.5.1，加两个静态字（`0x3F7D68` 字库缓冲 4,800×288；`0x141010` 跳到钩子），再把钩子写进 `0x78BC00` 空闲区。<br>**繁体** = 简体，加：字库读取的 5 条指令、线性取字回落 2 条、42 处界面文字、进关标题偏移表 117 项。 |
| 差异补丁 | 按程序头逐段求两份可执行文件的差异：47 条记录、589 字节，另有 8 条对照表行；整个补丁文件 1,172 字节，占 1 个扇区。<br>格式：32 字节文件头（`ZHTP`、版本、对照表行数、记录数、正文长度、正文按 u32 求和的校验和）+ 对照表行（行偏移、LBA、扇区数）+ 记录（地址、长度、数据按 4 字节补齐）。<br>构建时：在 Python 里按钩子的逻辑重放补丁，必须得到繁体可执行文件；钩子本身、钩子入口、字库缓冲字、音乐钩子 4 处、堆起点 5 个字、字幕段的 GIF 包缓冲（`0x798000`–`0x7A0000`）都不允许出现在记录里。 |
| 读补丁 | 钩子复制了 `0x1391B0` 的读盘流程，但不在堆上分配：`sceCdRead` 直接读到固定临时区 `0x1C00000`（上限 512 KB）。<br>读前先 `FlushCache(0)`；之后经非缓存镜像核对文件头和校验和，任一项不对就停在简体；应用完补丁，把临时区清零，再 `FlushCache(0/2)`。 |
| 进关标题 | 把 VT1 第 8 组整组（116 块，947,216 字节）复制到 DMY，其中 84 张标题换成繁体重编码，其余块原样复制。<br>繁体可执行文件里的组内偏移表（`0x41A2B0`，117 项）**每项加同一个常数**（360,746,864），指向“VT1 起点 + 组起点 + 偏移”，也就是 DMY 里的副本。<br>游戏的 3 处读取代码（`0x1D2BE0`、`0x1D2E44`、`0x3D0CC4`）都用“组起点 + 表[i]”作读取起点、“表[i+1] − 表[i]”作长度，所以整体平移后长度全部不变。 |
| 语言来源 | 记忆卡 1 号口的 `/BISLPS-25887L/LANG.BIN`，16 字节：`ZHLG`、版本 1、lang、~lang。lang = 1 时进繁体。<br>调试入口保留：开机按住 SELECT 直接进繁体，不读卡。 |
| 钩子 | 开机钩子和标题钩子在同一段：2,816 字节，放在 `0x78B640`–`0x78C4C0`（上限 3,712 字节）。<br>拉丁字形库载荷到 `0x78B610` 为止，其中 `0x78B600` 起 16 字节是它的运行时暂存区，所以从 `0x78B640` 开始。起点必须 64 字节对齐，因为读卡缓冲占一整条缓存行。<br>源码 `lang_hook.S`，构建脚本 `build_m1.py`。 |

DMY 用量：12,132,352 字节，DMY 共 122,558,928 字节。依次为：繁体字库、8 个文本成员、标题组、补丁文件。

## 2. 与技术方案不同的地方

1. **钩子没有放到 `0x790000` 段尾。** 该段 `0x798000` 起是剧情字幕每帧的 GIF 包缓冲（见 `tools/event_subtitles/apply.py`），之后还有运行时状态。
   - 钩子放在拉丁字形库段的空闲尾部 `0x78B640`–`0x78C4C0`，比实验 2 的起点 `0x78BC00` 前移。
   - 在整条测试路线（标题 → 读档 → 中场休息 → 剧情 → 地图）上做了存储监视。这一段只有三类写入：开机第 7 帧 BIOS 清零、第 62 帧载入可执行文件、钩子自己写的变量。
   - 所有随内容增长的数据都在 DMY 的补丁文件里，钩子本身不会再变大。
2. **字库读取指令、线性回落和标题偏移表都通过差异补丁带过去，钩子里不再单独写。** 钩子里只剩三个与内容无关的常量：补丁的 LBA、补丁扇区数、临时区地址。
3. **进关标题按“整组平移”处理，不是“只存变化的块”。** 偏移表里的长度是相邻两项之差，不能只挪其中一项，所以整组 116 块一起复制。这样不到 1 MB，和方案的预算一致。

## 5. 标题菜单的语言入口（M2）

**操作**：在标题菜单按 SELECT，弹出 Question 框。文字是「要将语言切换为繁体中文吗？（重新启动游戏后生效）」，在繁体模式下则是切回简体的问句，默认停在“否”。
- 左右键切换是/否；○ 确认，× 取消。
- 选“是”后写入记忆卡，然后显示 Report「语言设定已保存。」，写入失败时显示 Caution「无法写入记忆卡。」，按 ○ 关闭。
- 框打开期间，标题动画照常播放，但菜单收不到按键。

截图：`cmp-title-language.png`。

| 部分 | 实现 |
| --- | --- |
| 接入点 | `0x155CF8` 的 `jal 0x154FB0`（标题模式处理函数）改为跳到 `title_hook`。参数和返回值都是本帧的绘制包指针：主循环把它存在 `0x5238D8`，各模式按顺序往后追加。<br>钩子先调原函数画标题，再把消息框画在同一个包后面，所以框总是在最上层。 |
| 触发条件 | 只在标题子状态 `gp−0x7A2C == 3`（菜单等待输入）时响应 SELECT。按键状态在 `0x59C100` 的手柄结构里：`+0x14E` 是本帧按下，`+0x152` 是连发。<br>游戏的按键位：SELECT `0x0100`，START `0x0800`，上 `0x1000`，下 `0x4000`，左 `0x8000`，右 `0x2000`，○ `0x20`，× `0x40`。 |
| 消息框 | 用记忆卡界面现成的消息框：<br>· 创建 `0x36BBE0`，实例存在 `*0x6D5D68`<br>· 设定消息号 `0x36BC20` → `0x34F7E0`<br>· 输入 `0x36BC30(0x59C100)`：返回 1 表示选“是”，−1 表示“否”或取消<br>· 绘制 `0x36BCC0(包, dx, dy, 0)`：返回新的包指针<br>· 销毁 `0x36BD50`<br>绘制后要调用 `0x13AC90`（把 `*0x46E3A0` 置 1），否则框里的文字不画。 |
| 消息内容 | 消息共 24 条：文字指针表在 `0x4171F0`；属性表在 `0x42BF90`，每条 7 字节，依次是样式（0 Question / 1 Caution / 2 Report）、行数、默认选项（0xFF 表示没有是/否）、各行颜色。<br>游戏是在绘制时才按消息号去表里取文字，所以钩子在框打开期间“借用”一个消息号，把文字指针和属性换成自己的，关框时再还原。借用的是 19 号（问题）、22 号（完成）、11 号（失败）。<br>文字用正式码表编码，标点用这个界面的别名码（「。」`0x8FD2`、「？」`0x8FD9`、「（」`0x8FE8`、「）」`0x8FEB`）。同一份编码在繁体模式下自动显示繁体字形。 |
| 写卡 | 先确认 libmc 空闲（`sceMcSync(1) == −1`），否则按失败处理。<br>建目录用 `0x131E38`（Open mode 0x40）：返回 0 表示新建，−4 表示已存在。<br>新建目录时，先把可执行文件里的 `icon.sys` 模板（`0x414080`）标题临时改成「スーパーロボット大戦Ｚ／言語設定」（Shift-JIS，第二行从第 22 字节起），写出后立刻还原；再写出存档图标 `a20.ico`（`0x414450`，11,664 字节）。这样主机的记忆卡浏览器会把它显示成游戏数据。<br>最后写 `LANG.BIN`：Open(CREAT\|WRONLY) → Write → Close，每步用 `sceMcSync(0)` 等待完成。 |

### 5.1 为什么没有加第五个按钮

标题画面是一个带关键帧动画的场景（VT1 第 6 块，14 段）：前 10 段是 10 个对象各自的逐帧动画，四个按钮是第 6–9 段，每段约 85 KB，变长编码。

运行时的场景结构正好容纳 10 个对象：对象数组在 `*0x58E9A0+0x40`，每个 0x50 字节，后面紧跟帧区间数组 `+0x360`、`+0x374`、`+0x388`。按钮文字图集是 512×256 的 8 位贴图，空位够放两格。

所以加第五个按钮要做三件事：逆向按钮动画格式、扩大场景结构、重写场景载入代码。工作量远大于借用消息框，用户选了后者。

## 6. 新发现的问题

1. **繁体标题的字形和简体冻结快照对不上。** 用当前字库按生产渲染器重画简体标题，102 张全精度标题里只有 6 张和冻结快照一致，其余每张约差 1,000 像素。原因是快照用的是更早的字库，之后字形重新光栅化过。
   - 繁体标题如果用当前字库画，笔画会和简体标题略有不同。
   - M4 要先决定：繁体是否需要用快照当时的字库版本来画。
2. **钩子的汇编参数要用 `-mips3 -mabi=o64`。** 只用 `-mips3` 时，`sd/ld` 会被拆成两条 32 位存取，其中一条借用 `$at`。
   - 本次的临时区清零因此写进了垃圾值，已经修正。构建脚本现在会断言代码里不出现 `$at`。
   - 实验 2 的钩子有同样的展开，只是恰好最后恢复的寄存器值是对的。
3. **钩子区里有运行时会变的数据**：读卡和写卡共用的缓冲 `setting`（64 字节），以及对话框状态、借用记录等变量。校验钩子完整性时只比对 `setting` 之前的代码部分。
4. **第一版标题钩子把消息指针表写成了 `0x4271F0`**，正确的是 `0x4171F0`，所以框里显示的是借用消息号的原文，已经改正。
   - 这几次误写都在关框时还原了，不会留下改动。
   - 写钩子时，地址的高半段要按 `lui` 的进位规则核对。
