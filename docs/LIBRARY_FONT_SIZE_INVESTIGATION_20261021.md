# 图鉴与剧情正文：原生尺寸和控制符逻辑确认

> 后续实现与三版 LRPS2 验证见 [图鉴正文尺寸修复](LIBRARY_BODY_FONT_FIX_20261021.md)。下文保留修复前的原生逻辑调查记录。

2026-10-21。本轮按用户要求先确认原生程序逻辑，不实施补丁。核对 Original 原盘可执行文件、当前 Original 构建组件，使用 Unicorn MIPS64 执行未经修改的字体例程片段。未改生产语料、字体、构建逻辑或 ISO，未 commit/push。

## 确认结论与前轮纠正

角色图鉴正文为 **21×12**，机体正文为 **21×10**，术语正文为 **21×12**，默认剧情对白为 **22×11**。原生字符分类初始化只设置分类尺寸，不同步设置显式尺寸；遇到 width、height 或 space 控制符，会关闭本次绘制的字符分类选择，转用显式尺寸。

目前图鉴正文使用的恢复标签是 width=22、space=22，没有恢复字高，因此无法恢复图鉴原生 21×12。剧情默认尺寸恰为 22×11，在显式字高为 11 时，同样的横向恢复不会改变中文大小。这给出了两处表现不同的原生逻辑依据。

必须纠正前轮过度推断：

- 本轮核对的图鉴正文预设里，A、B 两组分类的**渲染宽高完全相同**。不能据字符代码范围分支的存在，推断这些正文里的不同中文字槽必然大小不同。
- 绘制函数退出时会恢复入口的分类开关，不能称开关永久泄漏到下一行。显式宽高、字距则没有在这个退出片段中一起恢复。
- 通用字体初始值 22×11 不是角色事典正文原生值。前轮提及的 `0x224A00` 预设没有绑定到截图正文，不能用它决定截图的字号。

## 参数表与调用绑定

全部地址均为 Original 虚拟地址。尺寸为原生字体参数，字高是原生渲染坐标中的值，不是用户放大截图里的像素高度。

| 显示面 | 正文描述表 | 分类 A 字形／推进 | 分类 B 字形／推进 |
| --- | --- | --- | --- |
| 角色事典 | `0x41F020` | 21×12／21×14 | 21×12／21×14 |
| 机体图鉴 | `0x41EEE0` | 21×10／21×12 | 21×10／21×12 |
| 术语正文 | `0x41F0E0` | 21×12／21×14 | 21×12／21×14 |
| 默认剧情对白 | `0x41E730` | 22×11／22×15 | 22×11／22×15 |

描述表 `+0x0E..+0x15` 的八个字节按以下顺序传给原生设置函数：

`A字宽、A字高、A横向推进、A纵向推进、B字宽、B字高、B横向推进、B纵向推进`。

不能把连续的“字形尺寸／推进尺寸”误当成两个不同分类的字形尺寸。

页面归属更正：早期把三个构造路径按错误顺序命名。现已按“viewport setup → renderer 构造 → vtable draw → metadata 原生标签”重新绑定。角色初始设置 `0x20E630` 经 `0x210140` 取得 `0x41F020`，9 行；其 renderer metadata 含“愛称”“声優”。机体 `0x20E900` 经 `0x2100A0` 取得 `0x41EEE0`，5 行，metadata 含“全長”“重量”。术语 `0x20EC50`／`0x20EE00` 经 `0x2101A0` 取得 `0x41F0E0`，5 行，metadata 含“：用語の切り替え”。描述表都经 `0x20E1B0` 写入对象 +0x10，由 `0x20E1E0 → 0x221130` 使用。三版原始指令／虚表／标签链见 [页面绑定证据](issue-assets/native-text-rendering-20261021/surface-bindings.json)。本更正不改变两个角色截图的原生 21×12 结论，但撤销对机体正文同高的推广。

默认剧情对象 `0x2098C0` 经 `0x20B920` 取得 `0x41E730`，构造器 `0x2097C0` 把参数复制到对象；vtable `0x447890` 的绘制入口为 `0x209420`，随后使用 `0x2212B0` 绘制姓名／正文。这里只确认该默认对白路径，不泛化到所有旁白、特殊窗口或 Back Log 样式。

## 每一行到底做了什么

图鉴 `0x221130` 逐行复制文本、补 NUL，在 `0x221220` 调用 `0x220DB0`。剧情 `0x2212B0` 也会拆行，并根据姓名／正文／特殊段落选择描述表后调用 `0x220DB0`。所以“剧情没有逐行初始化，图鉴才有”是不正确的解释。

`0x220DB0` 从描述表取八个尺寸字节，在 `0x220E14` 调用 `0x139D50`：

- 分类 A 渲染／推进写入 `0x46E368..0x46E36E`。
- 分类 B 渲染／推进写入 `0x46E370..0x46E376`。
- 分类开关 `0x46E378` 设为 1。
- 五种字符分类允许标志设为 1。
- **没有写入显式字形 `0x46E344/346` 或显式推进 `0x46E348/34A`。**

渲染器 `0x13A290` 把入口分类开关保存到 scratchpad `0x70000068`。绘制字形时，`0x13A618..0x13A79C` 根据开关选择显式参数或分类 A/B 参数。

| 控制符 | 原生处理器 | 写入 | 额外效果 |
| --- | --- | --- | --- |
| width (`32 xx`) | `0x13A470` | 显式字宽 `0x46E344` | 分类开关清零 |
| height (`33 xx`) | `0x13A490` | 显式字高 `0x46E346` | 分类开关清零 |
| space (`34 xx`) | `0x13A4B0` | 显式横向推进 `0x46E348` | 分类开关清零 |

这三个处理器各自只写一个维度，不把分类中的字高等参数同步到显式状态。

退出时 `0x13AC58..0x13AC64` 从 scratchpad 恢复入口分类开关；这个片段不恢复显式宽高或推进。所以行首或英文段里的 width/space 会让该次绘制采用残留的显式字高，但下一行又从分类尺寸开始。

两个人物的当前组件 PRDC“登场作品”字段均含以下实际原始字节结构：

```text

```

它显式设置字高 10，最后仍恢复为 10。若先按页面路径绘制该字段，再显示正文，则正文显式字高为 10：带恢复标签的首行变成 **22×10**，无标签普通行按正文分类尺寸为 **21×12**，行内 Geo/EFA 紧缩段后又恢复成 **22×10**。这是与截图相符的可执行状态序列；本轮没有把截图对应游戏进程的实际 RAM 采样当作已完成。

## 未修改原始指令的执行验证

以原始可执行文件加载段建立 Unicorn MIPS64 内存，执行 `0x139930`、`0x139E40`、`0x139D50`，三个实际控制符处理器、实际字形尺寸选择片段及实际退出开关恢复片段。没有用重写算法代替这些原始指令；显式字高 10 和 11 是受控输入，不是现场 RAM 读数。

共通过 **8 组显示面／继承字高组合，以及 3 个控制符处理器检查**。以继承字高 11 为例：

## 边界与后续修复约束

本轮是源码、二进制回读及原始 MIPS 指令片段执行确认，不是完整 PS2 模拟运行或 PCSX2 图形验收。Capstone 对 PS2 特有 128 位保存／恢复指令存在不兼容解码，本次指令执行只覆盖标准 MIPS 字体状态路径，不依赖这些错误解码。

截图没有 ISO 哈希；本轮没有 ISO 成员回读，也没有验证 BEST／SP 的对应地址。旧默认 `build/iso/zh-release-full-story/srwz-zh-current.iso` 当前不存在。当前 Original 组件的例程相等不等于截图所用 ISO 已绑定。

修复设计必须同时考虑图鉴的原生正文尺寸、英文段恢复参数、显式字高继承和布局测宽。不能直接决定统一为 22×11，也不能只保持分类开关为 1——那会令 width/space 的英文紧缩失去效果。当前仅记录这些约束，没有实施可执行文件补丁。
