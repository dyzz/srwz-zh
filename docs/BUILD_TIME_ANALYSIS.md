主要改动：

- **Rust 进程按线程复用**：为原有编码／解码函数增加长度分帧的内存管道协议，
  不再每次解码启动进程、每次编码创建临时目录并落盘输入／输出。保留原压缩算法、
  参数、解码限制和压缩后回解。最终完整 profile 共启动 **49 个 Rust 进程**，相对
  前轮约 5,912 次调用逐次启动，减少约 99.2%；各工作线程可以处理多条请求。
- **字体灰度结果只生成一次**：全量入口将 proposal 准备阶段的灰度图传给字体组件；
  组件继续核对 proposal 摘要、逐字灰度与量化／打包摘要。字体组件阶段从约 10 秒
  缩短到 3.6 秒。强制重建仍会重新生成这些灰度图，独立字体构建也保留现场光栅化。
- **独立归档并行**：MAPMODEL 标题／地形链提前启动；VEFF 菜单／教学标题在所需
  SLPS 数据就绪后与 STAGE 后处理并行。每条归档链内部仍按原顺序写入，等待全部
  结果成功后才输出完整组件。MAPMODEL 的块并发按 CPU 数量的一半设置，上限 8；
  本机 16 核使用 8 个 worker，8 核机器维持 4 个。
- **移除 UI 合并的无效等待**：6 张图集完成后即可组合 suite，与尚在运行的剧情构建
  重叠，消除原流程中约 3 秒的尾部串行等待。失败的图集不能进入 suite 合并。

## 2026-09-05：130.8 秒强制全量路径的当前热点

在完成日常增量优化的同一代码上，用临时函数计时包装器重新运行强制全量路径，
总墙钟 **129.792 秒**，与前次 130.81 秒接近。没有修改生产构建实现；使用同一份
正式语料，23 个最终组件仍与前次完整构建逐字节一致。此处不含 ISO 或下载。

这次主流程约为：字体准备／生成／验证 **20.9 秒**，剧情与资料库／图集并行构建及
图集合并 **17.2 秒**，全部资源集成 **90.1 秒**，收尾和缓存约 **1.6 秒**。
剧情主体自身 14.0 秒、资料库自身 14.4 秒、每张 UI 图集约 3.4 秒；这些任务并行，
不可把各自时间相加当作总耗时。

集成阶段主要热点如下。各行是集成主流程直接调用的耗时；子函数时间已经包含在内。

| 热点 | 当前墙钟 | 工作内容 |
| --- | ---: | --- |
| `build_terrain_names` | 24.253 s | MAPMODEL 的 80 个地形名块、475 处名称写入和重压缩 |
| `build_world_map_titles` | 15.136 s | 世界地图标题的冻结图像写入和重压缩；115 个成员中 101 个发生变化 |
| `_apply_stage_default_formation_names` | 10.019 s | 全关卡编队名写入、回读和压缩 |
| `build_veff_tutorial_titles` | 9.698 s | 教学标题效果贴图及压缩；其中压缩封装调用合计 5.760 s |
| 集成主流程的四次压缩封装调用 | 7.922 s | VT1 标题及 COMPDATA、NISV、第 0 个 STAGE workspace 的收尾压缩 |
| `apply_stage_keyword_popups` | 4.394 s | 关键词弹窗的库存核对、写入和压缩 |
| `_apply_full_stage_titles` | 3.477 s | 全关卡标题，包含标题图像和小块编码 |

MAPMODEL 两个顺序执行步骤合计 **39.389 秒**，约占整次强制全量的 **30.3%**，
是当前第一优先级。它已经使用冻结的标题图像，15 秒不能解释成重新 rasterize 标题。

字体三步分别为 **8.998 / 9.964 / 1.933 秒**。准备 proposal 与生成字体组件的代码都
调用字形 rasterizer；共享同一次构建中已生成的字形数据，是仍可消除的重复工作。
字体组件阶段的一次 `reencode_changed_suffix` 为 3.147 秒，不能把整段都算作光栅化。

本次共观察到 **4,408 次生产解压调用、1,504 次 Rust 编码封装调用**，当前实现通过
子进程执行这些操作。其累计耗时存在并行重叠，不能再加到总时间上，也不能将等待锁
的时间独立算成一个 CPU 热点。下一步应优先评估 MAPMODEL 与其他独立资源并行、
减少编解码进程往返、合并同关卡的多次写入和压缩，以及共享字形光栅结果。

此前的透明像素重复扫描已经不在大头中：`_alpha_plane` 全程 13 次调用累计
0.133 秒，PSMT4 swizzle／unswizzle 合计约 0.628 秒。编码表 `_validated_overrides`
仍被调用 13,519 次，累计墙钟 4.040 秒、线程 CPU 3.956 秒，可继续优化，但优先级
低于大归档编解码。不能再引用旧 cProfile 中透明像素扫描的 14.69 秒当作当前瓶颈。

原始证据位于 `work/benchmarks/build-20260905/hotspots-current/`：
`profile_build.py` 为临时计时器，各脚本 JSON 包含调用数、墙钟和线程 CPU，
`summary.json` 汇总主流程与直接调用。它只为粗粒度函数计时，未开启逐调用全局
Python tracing；当前热点数值来自本次补测，而非将旧 profile 按比例拆分成 130.8 秒。

有不同成本，未把 0.38 秒当作冷构建时间。

实现变化：

- 剧情主体保留共享依赖指纹及每个对白文件摘要，局部修改只压缩对应 STAGE 块；
  字体二进制指纹、共享配置、条件／说话人语料及实现变化会使缓存失效。
- 集成层新增真正的 STAGE 单独入口，避免为了一个 STAGE 块重建 SLPS、VT1、COMPDATA。
  编队名和关键词后处理只执行变更关卡，未变关卡的最终块和逐块验收统计直接复用。
  第 0 块、后处理依赖变化或旧缓存没有所需证明时走完整集成。
- 工作 ISO 的文件身份、布局和成员大小未变时克隆既有镜像，只替换变更成员；完整
  原盘证明和未修改成员证明得以复用。实际变更成员重新回读，配置要求的 UDF 回读也对变更成员重做；最终
  整盘仍计算 SHA-256。镜像大小变化、文件身份变化、实现或配置变化会退回完整重建。
- 去掉 ISO 刚完成全盘哈希后，外层脚本立即再读一次整盘的重复工作。
- 普通全量入口在构建代码及 UI 图集未变时复用同一组件流程，不再先重跑全部字体、
  图集和剧情。`--force-rebuild` 保留完整重算；`--release-proof` 使用完整 mkps2iso
  构建、全量语义回读和第二次确定性构建。

最终 ISO 都是 `48e9fdb974a2a1a75b3904381b6d72f1cc5868fc14a90ec980f019e534e1916c`。
测试完成后恢复原文；该测试 ISO 不作为最终交付候选。

这次实际改字的整合阶段从 106.89 秒降到 31.179 秒；受影响成员从 15 个
收窄为 `DATA/STAGE.BIN`。约 13 秒的 170 个 STAGE 主体构建仍存在，最终 STAGE 的
编队名、概要和关键词等后处理仍需执行，因此当前局部改字尚未成为单关卡独立构建。


本轮消除的重复工作：

- **字体元数据引发全资源重建**：`ui_selection` 记录收录语料的文件及摘要，本身不生成
  字形或编码字节。原实现把其摘要变化传播到 15 个物理成员，包括 NISV、VEFF、MAPMODEL。
  现在使用共享的字体语义指纹，排除且仅排除这个字段；字体映射、别名、字形和来源等
  任何其他字段变化仍重建相关消费者。剧情组件也保存这个指纹，避免在下一轮因为
  旧 proposal 引用再重建一次。
- **没有受影响成员仍执行 writer**：原实现条件为 `affected_members or reasons`，
  上游报告元数据变化也进入整合函数。本轮首测没有受影响成员，却花了 16.94 秒整合。
  现在只核对上游验收状态、复用已验证输出并更新报告中的输入锁。
- **UI 图集检查重复生成**：文本路径核对已有图集配置、manifest、直接输入和最终
  归档的哈希；不再重组字节所有权图。全量路径各构建一次 atlas／suite 后核对落盘
  结果与内存产物，省去紧接着由 `verify` 重建第二次的成本。
- **逐像素重复扫描整张图**：NISV 菜单的透明像素计数把 `_alpha_plane(...)` 放在逐像素
  生成器里。profile 中 `_stored_palette_index` 被调用约 6313 万次，`_alpha_plane`
  累计 14.69 秒。现在生成一次透明度表，再用 `count(0)` 计数；统计值不变。
- **重复验证同一贴图地址映射**：PSMT4 每种尺寸／页布局的置换关系只计算并验证一次，
  用最多 8 项的进程内缓存复用。每张图仍检查尺寸、长度和 4-bpp 像素范围。
- **未改字节逐个进入 Python**：归档差异统计先用 4096 字节块比较，再枚举发生变化的块，
  保持差异偏移、范围和所有摘要不变。
- **刷新开关无条件使缓存失效**：完整输入及输出均未变化时，`--refresh-manifests`

## `rebuild_zh_font.py` 实际做了什么

脚本名称容易让人以为它只生成字体，实际它是中文生产链的总入口：

1. 准备并校验全局中文字体及字形映射。
2. 构建字体组件并执行字体回读校验。
3. 重建 reviewed LIBRARY（约 2,709 个条目、4,921 个字段引用、784 个数据块）。
4. 重建 170 个 STAGE 的剧情组件（约 84,338 条原始记录）。
5. 构建并校验 6 组 UI atlas 以及 atlas suite。
6. 重新整合全量 story 组件，执行解码、写入、压缩和结构验证。
7. 接入 AIDDATA、TRICMN 的锁定索引快照并组合最终组件。

这里的 `--force` 是有意的：它保证全局字体或编码表变化能够传播到所有消费者，避免
生成“表面成功、实际混用旧组件”的结果。AIDDATA 和 TRICMN 的普通构建使用锁定快照，
不会因为每次构建而重新栅格化全部图像。

## STAGE 编码映射重复验证

优化前，`encode_stage_message()` 为每条 STAGE 记录复制同一份字符 override，并重新创建
`PreparedTextEncoder`。因此 `_validated_overrides()` 在一轮构建中被调用 `84,781` 次，
累计约 `41.22 秒`；这不是必要的文本安全检查，而是错误的对象生命周期。

当前实现为普通文本、运行时姓名占位符、关键词链接、占位符与关键词组合四种语义各创建
一个只读 encoder，并在 170 个 STAGE worker 间共享。字符映射仍在创建 encoder 时完整
验证，`:` 的原始 `0x3A` 和 `《》《》` 的 `0x8173/0x8174` 表面规则也保持不变。

同口径结果：

| 项目 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 单线程 STAGE profile 实际时间 | 80.60 s | 36.05 s |
| `_validated_overrides()` 调用 | 84,781 | 277 |
| `_validated_overrides()` 累计时间 | 41.22 s | 0.06 s |
| `encode_stage_message()` 累计时间 | 47.99 s | 3.58 s |
| `repack_stage_texts_in_place()` 累计时间 | 58.78 s | 13.87 s |
| 正常 12-worker STAGE 构建 | 约 45.14 s | 18.03 s |

优化前后 `STAGE.BIN`、`HB.BIN` 和组件报告 SHA-256 完全一致。这一项保留校验本身，只把
校验从“每条记录一次”移到了“每份映射一次”。相同的 prepared encoder 也用于最终 ISO
STAGE 字节回读；强制完整回读实测由 `56.47 秒`降到 `28.98 秒`。

## STAGE 解压、解析和定点回读

继续 profile 后确认，优化后的 STAGE 构建仍重复消费同一份源数据。205 个压缩 chunk 原本
在 ticker 全盘发现、Z Report 全盘发现、未翻译覆盖检查和实际构建之间被解压 629 次；
再加上 182 次压缩 round-trip，一轮构建共有 811 次解压、993 次 Rust codec 子进程。

当前在本轮构建开始时把 205 个 Rust `DecodeResult` 保存在内存中，供所有只读消费者复用。
一次解压全部源 chunk 实测 `0.62 秒`，解压后数据共 `11,687,504` 字节；因此不值得增加
磁盘缓存格式。源解压由 629 次降到 205 次，全部 codec 子进程由 993 次降到 569 次。

同一个翻译 STAGE 过去还会在 `build_stage()` 和 writer 内连续解析两次源结构。writer
现在接收调用方已经获得的只读 `StageParseResult`。写完以后也不再重新发现整个 STAGE
的未改动区块，而是定点读回每个唯一写入：逐一核对指针、说话人、正文、NUL 终止符和
payload 边界。压缩流仍执行 Rust 解压 round-trip；完整 ISO 验证器仍独立解析最终成员。

这两项不删除写入证明，只删除重复发现。同一份 `STAGE.BIN`、`HB.BIN` 和组件报告的
SHA-256 均保持不变。独立 STAGE 构建的后续实测为：

| 状态 | worker | `real` |
| --- | ---: | ---: |
| prepared encoder 基线 | 12 | 18.03 s |
| 源解压缓存 | 12 | 17.00 s |
| 源解压缓存，worker 扫描最优点 | 4 | 16.71 s |
| 再复用源 parse | 4 | 14.89 s |
| 当前定点输出读回 | 4 | 13.55 s |

源解压缓存后的 worker 扫描为：1/2/4/6/8/12/16 workers 分别需要
`23.34/17.35/16.71/17.11/17.32/17.52/17.56 秒`。4 workers 是甜点位；继续增加
并发会让短命 Rust 进程相互争用。当前 4-worker 时间轴中，Rust 编解码子进程的去重
墙钟覆盖为 `9.89 秒`，重编码阶段覆盖 `11.64 秒`，STAGE 重排覆盖 `5.69 秒`；这些阶段
互相重叠，不能相加当作总时间。

## 为什么优化前完整回读要 56 秒

`tools/verify_full_story_iso_content.py` 的回读不是只读取一个整盘校验值，而是按成员和
语义逐层检查：

- 读取 ISO 中需要验证的成员，并检查成员大小及 SHA-256；
- 对字体、组件、文本 corpus、translation lock 和源归档反复计算哈希；
- 解压并解析 STAGE、LIBRARY、NISV、COMPDATA、SRVC 等结构；
- 逐项核对翻译 entry 集合、源文本 preimage、对白/说话人对应关系和运行时替换 token；
- 检查编码禁用项、可见 ASCII/空格规则、图像逻辑索引、压缩流 round-trip；
- 检查 replacement 的固定 LBA、容量预算、未替换成员和 manifest 一致性。

优化前回读计时为：

```text
real 56.28s
user 50.87s
sys   4.77s
```

`user` 时间明显高于 `sys`，表示主要工作在本地 CPU 上完成，符合“解析、解压、比较、
哈希”混合负载，而不是单纯等待磁盘。相比之下 ISO 组合只有 `9.45 秒`，所以当前瓶颈
在验证器的内容/结构检查，而不是 mkps2iso 写盘。prepared STAGE encoder 接入后，同一
候选的强制完整回读为 `28.98 秒`。

   物理成员级增量模式。未受影响的冻结资源不重新 rasterize、swizzle、压缩或逐像素
   回读，只检查现有输出、manifest 和输入锁是否仍能对应。
2. **资源制作路径**：只有修改贴图文字、布局、调色板、字体源或对应 writer 时，才重跑
   该资源的完整生成与结构/像素验收，人工审图通过后更新冻结件和锁。
3. **显式冷复验路径**：`--force-rebuild` 保留完整重算，用于调试生成器、改变资源契约或
   需要证明从源输入可重现时；它不再代表普通开发 build。
4. **ISO 路径**：日常候选生成到 `build_iso.py` 即可，完整 ISO 语义回读改为发布候选、
   固定 LBA/成员映射变更或专项排错时显式执行。相同 ISO 的回读缓存仍可用于快速复核。
5. **Rust 优先级下调**：NISV/VEFF/MAPMODEL 的像素循环在强制冷复验中适合 Rust，但默认
   路径已通过冻结成员复用消除这部分等待，先不为日常 build 重写一套实现。若冷复验仍
   成为高频需求，再批量迁移这些 kernel。
6. **下一缓存边界**：正常 cache miss 已降到约 47 秒；若仍需优化，优先把字体阶段和
   atlas suite 做成各自的内容寻址节点，使仅改剧情 writer 时不必重跑未受影响的字体与
   atlas。当前顶层无改动闭包已经由完整缓存覆盖，不再为热缓存重复设计第二套捷径。
