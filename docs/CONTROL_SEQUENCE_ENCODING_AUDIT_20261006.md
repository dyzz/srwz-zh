# 控制序列被字形编码改写：原因与扩展审计

2026-10-06。初次分析解释 V042-005 的具体原因，并确认另外 22 处控制字节
变化；用户随后授权修复、commit 和 push。本轮已补齐共享编码器、分类／排版
保护和 SP 独立字节校验。下文保留修复前证据，扩展修复结果见文末。

三角误显示为圆圈是汉化写回改变了原生控制字节，不是日文原版的按键规则错误。
原版／旧版／第一轮修复 LRPS2 对照见 [V042-005](V0.4.2_POST_RELEASE_ISSUES.md#v042-005)。
扩展修复前的 SP 另有 22 处控制字节变化，分布在 21 条文案；新增项的具体画面
影响尚待同页运行对照，不能把字节检查通过写成所有界面运行通过。

## 一个完整例子

原版武器列表底部文案使用 `<-3>` 选择三角图标，原生字节如下：

```text
字符／语法： <    -    3    >
原盘字节：   3C   2D   33   3E
```

共享解码器遇到字节 `31` 至 `35` 时，会读取后续一个参数字节并写成标签记法。
因此这里的 `33 3E` 被序列化为 `<height:3E>`，整段成为：

```text
<-<height:3E>
```

这是工具的无损文本记法。`height` 这个名称不代表游戏此处真的执行高度设置；
在原生 `<…>` 内联图标语法中，`33` 是选择数字的 ASCII 字节。
原始数据的同一字节，在不同语法上下文中可以承担不同角色。

旧编码器识别后半标签，却没有将整段识别为一个不可改写的原生选择器。
它处理前半部分的短横线时，应用普通正文的字形覆盖：

```python
glyph_overrides["-"] = 0x9868
```

这个覆盖用于中文字体中的可见短横线。用于正文时合理；用于控制序列的 ASCII
负号时，会把一个协议字节变成一个双字节字形码：

| 阶段 | 实际字节 | 含义／结果 |
| --- | --- | --- |
| 原盘 | `3C 2D 33 3E` | 原生 `<-3>`；LRPS2 显示三角 |
| 旧汉化写回 | `3C 98 68 33 3E` | 选择器中的 ASCII 负号已丢失，长度由 4 增为 5；LRPS2 显示圆圈 |
| 当前修复写回 | `3C 2D 33 3E` | 整体保护并恢复原生字节；LRPS2 显示三角，按三角打开驾驶员报告 |

根因是控制语法识别不完整，使控制字节经过了可见字形编码。输入处理未修改，
也没有修改图标贴图。圆圈是错误字节在实际运行中的显示结果；尚未逆向证明
具体内部错误分支，因此不将“所有错误输入都固定回退为圆圈”作为结论。

第一轮修复在处理普通字形覆盖之前，将整个 `<-<height:3E>` 作为运行控制符输出。
本轮扩展为完整控制语法，普通可见短横线仍使用中文字形码。

## 为什么旧校验能通过

汉化回读表知道 `98 68` 对应可见字符 `-`，所以：

```text
错误字节：3C 98 68 33 3E → 解码文本：<-<height:3E>
正确字节：3C 2D    33 3E → 解码文本：<-<height:3E>
```

两组字节解码成相同文本。这种“回读文字与译文一致”的检查验证字形身份，
无法单独验证控制协议的原始字节。扩展修复前的 SP 独立验证器在系统文案上只比较
`decode_text(...).text == expected`，因此会漏过下面两类改变。
已完成的成品回读与测试结果仍有效，但其证明范围不能扩大为所有控制语义正确。

同样，`control_notation_tokens('<0>')` 已将整个 `<0>` 标为运行替换符；
实际编码器却没有相应的整体输出分支，仍会逐字应用数字覆盖。
分类／排版保护与字节写回保护两套规则并未完全一致。

逻辑及其他归档不属于此次 213 处的计数范围。

22 处字节变化分布在 21 条文案；`sd/compdata/944A0` 同时含 `<9>` 与 `<8>`。
它们是数字内联图标，并非都表示控制器按钮。上述 22 处确认的是协议字节
改变，尚不能按 22 个已复现画面 bug 登记。

可直接核验的文案例子：

- `sd/compdata/935F0`：“将光标移至此处按 `<0>` 可进入机体选择。”
- `sd/compdata/944A0`：“还有小队攻击用的 `<9>`、攻击小队全机的 `<10>`、
  TRI 攻击用的 `<8>`……”
- `sd/compdata/9F3F0` 与 `sd/compdata/9F440`：驾驶员查看提示中的
  `{4.4.0}`，无损记法为 `{<space:2E><space:2E>0}`。

`<10>`、`<23>`、`<38>` 等当前保留了原始字节：它们的首数字落在 `31..35`
中，解码时两个数字恰好都被放进标签，写回未经过字形覆盖。
例如 `<10>` 序列化为 `<<color:30>>`，重写仍为 `3C 31 30 3E`。
不能从这些序列当前没变推断数字选择器都已有完整语法保护。

花括号例子也有相同的上下文歧义：原生 `{4.4.0}` 被拆成
`{<space:2E><space:2E>0}`，两个 `4.` 保留为原生标签字节，而最后的 `0`
被当作正文数字。`space` 标签名同样是工具记法，不足以证明真实花括号样式语义。

本篇作者语料也存在相同语法，并使用共享编码器。这提示要检查主篇写回路径，
但本次未对 Original／BEST 最终 ISO 做同组读回，不将 SP 结果自动推广为
三份成品都有同样数量或同样可见故障。

## 旧编码器仅在构造输入中发现的边界

原生 `%02d` 被通用解码器展开为 `%0<width:64>`。
直接把这个无损记法交给扩展修复前编码器，会得到
`98 65 82 4F 32 64`，原生应为 `25 30 32 64`。
这是 `%` 与 `0` 再次漏入字形覆盖的函数级反例。

受检语料未检出这一 `%02d` 形式，不能把它列为现存成品问题。
当时发布字体收集器会将 `%0<width:64>` 识别为未支持占位符并拒绝，
存在构建前保护；该保护不等同于编码器本身能正确保留此语法。
`%2d → %<width:64>` 已受编码器专门保护，当前字节保留正确。

## 实现与验收范围

仍需对武器类型帮助的 PLA／TRI 图标及 `<0>` 做日文原盘与修复 SP 的同页运行对照。
花括号参数已在下述驾驶员提示到达同一运行字段，其他使用位置仍需单独验收。此次短程 UI 探索未到达目标帮助页面，不据此
作新增画面故障或修复通过的结论。PCSX2／人工亦未执行。

实现上应让提取、控制符分类、编码器、独立验证器采用同一套完整控制语法：
控制片段保留原生字节，普通文字仍用汉化字形表。不要全局取消数字、短横线或
百分号的字形覆盖，也不要将所有角括号内联图标统一替换为某个按钮。

验证应比较每条文案中有序控制片段的原始字节与写回字节，控制序列确需修改时
使用明确许可；正文继续按中文回读检查。回归例子应包括 `<0>`、`<8>`、`<9>`、
`<10>`、`<-3>`、`{4.4.0}`、`%2d` 和混合记法 `%02d`，再绑定最终 ISO 与指定
运行事件。新增项现已完成源修复与字节验证，已有三角修复继续保持。

## 本轮扩展修复

共享 `CONTROL_NOTATION` 识别完整数字图标、数值花括号、格式占位符及美元变量，
包括它们经通用解码器展开后的标签记法。分类、字体／排版保护、编码写回使用同一
套语法；编码器先恢复原生 ASCII 控制片段，再处理正文的字形覆盖。
`two_byte_visible_spaces()` 保留格式串中的空格标志，只转换可见空格。
既有原始字节记法 `{12}` 继续表示 `0x12`，不改成一个新定义的数值控制。

比较原生控制字节和顺序。SP 最终 ISO 的系统文案、模板和 ticker 回读调用它。

确认它们即使解码成相同文本也会被拒绝。普通可见数字／短横线、布局标签、原始
