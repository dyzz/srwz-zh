# 三合一语言盘：实现说明与游戏程序改动

2026-11-19。本文说明“一张碟三种语言”（简体 / 台湾繁体 / 香港繁体）是怎么做出来的，并列出相对于简体单语盘，游戏程序（可执行文件）被改了什么。

适用版本：本篇 Original（`SLPS_258.87`）、BEST（`SLPS_732.70`）、Special Disc（`SLPS_259.20`）。

过程记录和逐项验证见 `ZH_HANT_HK_TW_PLAN_20261118.md`（已删除，原文见提交 eb9c1f90）、`ZH_HANT_SINGLE_DISC_M4_20261117.md`（已删除，原文见提交 eb9c1f90）、`ZH_HANT_SP_DUAL_PLAN_20261117.md`（已删除，原文见提交 eb9c1f90）。本文只讲现在的最终形态。

## 1. 一句话概括

- 仓库分别保存简体、台湾繁体和香港繁体的语料、术语表及运行时文字。一条命令在当前目录构建，产物是每个版本一张三合一盘。
- 盘上的默认内容就是简体盘。繁体的文本、字库、贴图另存一份，放在原盘本来全零的占位文件里。
- 游戏开机时多执行一小段我们加的程序：读存档卡上的语言设置，如果是繁体，就在内存里把“读哪个文件”和“程序里的文字”改成繁体那一份。
- 游戏本身的引擎逻辑没有改。简体模式下，除了那段开机程序和标题画面的设置面板，运行内容与简体单语盘相同。

## 2. 语料与构建

### 2.1 三种语言的来源

| 语言 | 语料位置 | 说明 |
| --- | --- | --- |
| 简体 | `corpus/zh`、`corpus/glossary`、`corpus/runtime` | 主语料 |
| 台湾繁体 | `corpus/zh-hant`、`corpus/glossary-zh-hant`、`corpus/runtime-zh-hant` | 按文件和条目直接使用台湾译文 |
| 香港繁体 | `corpus/zh-hant-hk`、`corpus/glossary-zh-hant-hk`、`corpus/runtime-zh-hant-hk` | 已用原合盘的香港语料初始化，可独立编辑 |

默认构建先检查三套语料的覆盖情况。各语言分别维护译文，缺少文件、条目或译文时，构建会指出缺项并停止。SP 关卡复用译文时按目标位置读取所属语言的语料 ID。图库菜单、无 BGM 提示和 Data Link 奖励说明从该语言的 SP 产品配置读取。

繁体另有自己的码表、字库配置、版式词表和贴图配置，都在 `config/zh-hant/` 下。港台共用一套码表和字库（两地字形取并集），贴图也共用一套（台湾字形）。

### 2.2 构建方式

```
export SRWZ_LANGUAGE_PYTHON="$PWD/.venv/bin/python"
python3 tools/build_editions.py
```

默认生成本篇、BEST、SP 各一张三合一盘，分别位于 `build/iso/test/multilang-{original,best,sp}.iso`。只构建 SP 可运行 `python3 tools/build_editions.py --editions sp`。添加 `--force-rebuild` 会重跑组件构建。开发工具仍可用 `--single-language` 选择单语路径。

隔离实验可用 `python3 tools/build_editions.py --out-dir build/iso/test/experiment` 将三张合盘镜像和各自的回执写入专用子目录。单语候选盘、日志和组件缓存仍由同一构建锁串行管理。

| 版本 | 三种语言如何生成 | 最终制盘 |
| --- | --- | --- |
| 本篇、BEST | 每种语言冻结自己的语料、码表和贴图配置，构建各自的候选镜像。BEST 继承同地区的本篇前端。 | 从三份候选镜像取差异，写入对应版本的三合一盘。 |

两处复用边界如下。

- **贴图差异按归档复用。** 用本篇简繁资源、日本原图、SP 当前及原始资源的实际字节、块索引、存储模式和处理工具身份计算指纹。任一输入变化会重算对应归档。生成逐区域审图材料时执行完整处理。
- **预览及文字基线按整盘内容复用。** `preview`、`text-canary` 各自保存上次通过 xdelta 编码、解码和整盘校验的补丁。源盘、目标镜像和编码器等输入匹配且缓存负载校验通过才复用。一次地区构建内部，用私有 APFS 克隆把已验证的基线交给后续工具，读取前核对大小及 SHA-256。快照完成时清理临时镜像。持久缓存分港台、按产物覆盖，本轮实占约 263 MiB。

仍在执行的步骤中，台湾单语盘写入并独立回读最新字幕。该例的五个最终正文组件都因输入指纹改变而重建，报告中的差异还包括字体提案、验证清单和读取译文用的字典。逐文件比较 A、B 两份台湾组件报告，只有 SRVC 的 `BTL/SRVC.BIN` 改变；system、stage、frame、image-labels 四个组件的输出文件全部相同。这四项是进一步细分依赖的候选，目前仍执行原校验。台湾最终正文构建与回读阶段耗时 50.89 秒（优化前 53.08 秒）。香港单语镜像的 SHA-256 未变，可以复用已验证成品，但仍需生成地区输入快照。每个地区的分步耗时与缓存命中项在 `build/multilang/logs/sp-zh-hant-{tw,hk}.log` 的 `[sp-view]`、`[sp-cache]` 行。

字节复验分两组进行。原语料 A 在优化前后的三张 ISO 整盘 SHA-256 均与第 7 节相同。修改后 B 在两套代码上的三张 ISO 也逐张一致，本篇、BEST 等于 A，SP 成品变为 `912eb34345b179f8d9b488f3defd6bd3838b35bea26fd4c5c0cc6552ceead7e2`。用成品回执的 LBA 直接读取 B 镜像中两份 `BTL/SRVC.BIN`，按各自码表解码第 11 块第 86 条，台湾读回「我才不會輸給」，香港读回「我可不會輸給」。原始分步日志、计时、整盘哈希及验收记录在 `work/analysis/sp-incremental-build-20261119/`。

对改动后的 B 成品另做 ARMSX2 验证。本篇、BEST、SP 各冷启动三次，分别核对无设置时的简体、保存后的香港繁体、按住 SELECT 强制进入的台湾繁体，并打开设置面板。九次全部通过。字幕内容的逐字证据来自上述 ISO 回读。本轮单元测试发现 1,051 项，1,042 项通过、9 项跳过。

恢复 A 时，本篇的私有构建目录仍有该输入上次生成的回读报告，原有验证器拒绝覆盖。将该报告移到本次证据目录，再走默认入口重新回读。恢复后的三张 ISO 均与 A 的原始整盘哈希一致，港台战斗台词均读回原文。两次 A → B 比较均一次完成；恢复过程另计。

### 2.6 在一张 SP 三语盘上并行重建战斗字幕（分支验证）

`tools/zh_hant/build_sp_battle_disc.py` 读取一张由 SHA-256 锁定的三语底盘。三个进程同时从 SP 日文原始 SRVC、各自的语料和已验证的字库码表生成字幕归档。每个进程回读所有字幕记录。主进程核对上一版三区归档的哈希、槽位大小和边界，把三个归档写入同一张临时盘，再从成品读回。此路径无需创建任何单语 ISO。

沿用 2.5 的 A 和 B，同机实测分别为 **7.89 秒**和 **6.37 秒**，均含 SP 成品整盘 SHA-256。A、B 分别与对应的完整构建逐字节一致。这里测量的是已验证底盘上的 SP 字幕资源更新，2.5 的 224.68 秒还包含本篇、BEST 和 SP 的完整默认调度。这个专用入口覆盖固定槽位战斗字幕。默认全量入口见下节。

### 2.7 SP 全量单次制盘

简体从日文 SP 原盘和哈希锁定的基础补丁读取数据。台湾和香港分别生成继承本篇的预览与文字基础资源。每个地区各自处理字体、系统文本、战斗字幕、STAGE、图像标签、图集和剧场资源。文件成员的改写、重定位以及 ISO9660/UDF 目录改动以二进制块和偏移表（`.spview`）保存。独立正文验证器按这些偏移读取完整的逻辑盘面。最后，布局器把简体资源、港台差异和开机语言钩子写入同一份暂存文件，再发布到默认输出路径。

地区缓存绑定构建输入、支持文件、本篇成员内容和标题版本。命中后重算逻辑盘面的 SHA-256。香港使用自己的战斗台词；对台湾字符串字典的依赖按共用 Data Link 页面实际取用的译文校验，台湾贴图来源也单独纳入校验。这样能复用香港资源，同时捕获确实会改动香港盘面的台湾译文。普通重建按归档复用已核验的贴图差异。每个地区保留最近三组已验证资源，发布前再次核对三区输入身份。2.3 至 2.5 的阶段名和耗时记录的是旧的单语中间盘流程。

本轮在 `zh-hant-dual` 上只选择 SP。A 从三套原语料运行 `--editions sp --force-rebuild`，保留内容寻址压缩缓存；B 只修改 2.5 的同一句台湾台词，随后运行 `--editions sp`。计时为入口的墙钟时间；独立整盘散列和模拟器启动另计。下表的地区任务并行，不能相加。

### 2.8 调度重叠与常驻排版进程（2026-11-19 晚）

三处改动，产物逐字节不变。

**1. SP 区域编译与本篇同时起步。** 原来 SP 三区资源排在本篇＋BEST 整个阶段和两次合盘之后。

- 简体区域不需要本篇前端，构建一开始就编译。
- 繁体区域也在一开始启动，先做不读本篇的步骤（复制输入、支撑目录、语料视图、字库、配置与标签）；走到继承基线之前，等本篇构建写出前端回执再继续。
- 本篇候选构建在 `components` 阶段结束时写出前端回执（`work/cache/editions/sp-frontends-early/`，内容和校验方式与 SP 单独构建时的前端回执相同）。组件成员在这一刻已经定稿，早于本篇自己的制盘、回读和字幕。

**3. 排版引擎改为常驻进程。** `tools/srwz/js_layout.py` 原来每个批次启动一个 Node 进程，启动加载引擎约 45 毫秒。一次构建有几千个批次（SP 一个关卡对白组件就有 354 个）。现在进程保持运行，每个批次是一行请求、一行应答；并发调用各用各的进程，空闲的放回一个小池子；进程异常时退回到原来的一次性调用。`SRWZ_JS_LAYOUT_ONESHOT=1` 恢复旧行为。

### 2.9 克隆记账、系统调用克隆与 SP 直接出盘（2026-11-19 夜）

接着 2.8 的三处改动，产物仍然逐字节不变。这一节的数字是在另一个会话改过战斗台词语料之后测的，三张成品的参考哈希随之变为本篇 `76c92088…`、BEST `4fff71f7…`、SP `87a34181…`。

**1. 克隆带来的摘要批量写入。** 流水线为每次构建建私有工作区，把冻结的输入和上次验证过的中间产物放进去（macOS 上是写时复制，不占空间）。每放一个 1 MiB 以上的文件，`file_identity.record_clone` 就把 4 MB 的 `work/cache/file-identity.json` 整个读入、合并、重写一遍，还要拿文件锁。本篇每个工作区有 351 个这样的文件，SP 区域一百多个，六七个进程同时抢锁。

- 现在克隆带来的摘要先攒着，满 256 条、超过 2 秒或进程退出时一次写入；64 MiB 以上的文件（光盘镜像）仍然立刻写。
- 本进程自己哈希出来的摘要保持原样，立刻写入，其他进程马上可用。
- 没写入的记录最多让那个克隆文件被重新哈希一次，不影响正确性。

**2. 克隆改用系统调用。** `release_inputs.copy_file` 原来每个文件启动一次 `cp -c`，现在直接调用 `clonefile`，不可用时退回 `cp -c`，再退回普通复制。

这两项让本篇的 `prepare` 阶段在普通重建里从 16.7 秒降到 1.4–2.6 秒，SP 区域的起步开销从约 15 秒降到约 5 秒。

**3. SP 在同一个进程里直接出盘。** 提前启动的 SP 构建编译完三区后不退出，等调度器写出 `go` 标记（本篇和 BEST 全部通过、繁体贴图检查通过之后才写），然后直接布局、写盘、回读、发布。省掉重新启动和对刚封存资源的再次整盘摘要。其他版本失败时调度器写 `go.cancel`，SP 不出盘。提前构建没有成功时（本篇复用了已验证镜像、或编译失败），仍由原来的 SP 出盘步骤处理。

### 2.10 SP 繁体视图按实际读取复用（2026-11-20）

改动前，SP 繁体区域的输入指纹包含全部输入文件，任何一个文件变化都会把字库、配置重绑、继承基线、菜单图集全部重做一遍（约 45 秒），哪怕改的只是一句 SP 战斗台词。

**做法。** 视图拆成两个阶段，各自作为独立进程运行（`language_view.py --stage …`）：

| 阶段 | 内容 | 读不读本篇构建 |
| --- | --- | --- |
| `font-configs` | SP 字库、配置与图像标签重绑 | 不读 |
| `baseline-atlas` | 继承基线、基线后的标签与关卡标题、菜单图集 | 读 |

`tools/srwz/step_memo.py` 负责“这个阶段要不要真的跑”：

- 第一次运行时，阶段里每个 Python 进程都通过审计钩子（`tools/srwz/step_trace/sitecustomize.py`）记下自己打开读取的文件、列出的目录、克隆的源文件。
- 记录保存每个读取当时的内容摘要：工程内的文件取阶段开始时的内容；仓库其他位置或本篇工作区里的文件取阶段结束时的内容。本篇工作区的位置每次构建都变，所以按“根的名字 + 相对路径”记录。
- 阶段在工程里新增或改写的文件（包括它改写的工具脚本常量）、删除的文件、建立的符号链接，都存进记录。
- 下次在新工程里，只要某条记录的所有读取内容都没变，就不运行阶段，直接把记录里的文件放回去。

钩子看不到的依赖由调用方放进“作用域”，作用域变了记录就不会被采用：工具源码整体摘要、解释器、被调用的外部程序（node、xdelta3）、压缩器可执行文件、xdelta3 按文件名读取的基线和光盘、`SRWZ_*` 环境设置、工程的全部文件名。

**开关。** 记录放在 `work/cache/editions/sp-views/<语言>/stages/`，每个阶段保留最近 4 条。`--force-rebuild` 不使用记录。`SRWZ_SP_STAGE_MEMO=0` 关闭。`SRWZ_SP_STAGE_VERIFY=1` 时即使命中也真实运行并与记录比对。

**验证。** 台湾区域，同一份输入：

| 跑法 | 秒 | 最终资源摘要 |
| --- | ---: | --- |
| 两个阶段真实运行并留下记录 | 80.1 | `28a35d82…` |
| 两个阶段都取回记录 | 40.0 | `28a35d82…` |
| 强制全量（不使用任何记录和缓存判定） | 91.7 | `28a35d82…` |

- 继承基线阶段会改写两个工具脚本里的哈希常量。最初把 `tools/` 整体排除在产物之外，取回时漏了这两处，随后的“保留基线镜像身份”校验报错。现在产物覆盖整个工程，`tools/` 只在读取一侧按整体处理。

修正的调度问题：本篇构建直接复用已验证镜像时，现在也立刻写出前端回执（成员校验与真实构建后相同），提前启动的 SP 不再被取消。

**这个场景下两个阶段都没有命中，原因是如实的依赖，不是漏洞。** 复用模块未命中时会打印是哪些读取变了：

- `font-configs` 读了被改的台词文件和 `config/zh-hant/readback-literals.json`。字库步骤要扫描全部语料确认每个字都有编码，并且在字库提案、清单、就绪报告里逐个写下每个语料文件的哈希。简繁对照字典由全部语料生成，任何一句变了它都会变。
- `baseline-atlas` 连带未命中：上一阶段重跑后，字库提案等文件里的语料哈希变了，SP 输入锁（`config/editions/sp/inputs.json`）随之改变。

也就是说，字库的二进制产物在这次改动前后完全相同，但它的来源记录按设计就应该不同。按文件内容判断的复用因此只在“阶段读到的文件确实没变”时生效，例如只改了别的语言的语料。

另一处同源的损耗：台湾、香港的本篇构建在语料改动后用不上上一次构建的增量种子（日志里是 `previous validated component caches: unavailable`），每次做完整的组件重建，约 75 秒，简体同样情况下约 17 秒起。我的判断是视图会重新生成配置里的语料锁值和对照字典，增量逻辑把这看成“组件定义变了”；这一点没有逐行证实。

**没有做的验证：** 香港区域没有单独做“取回记录对强制全量”的对照。取回记录在真实语料改动场景里没有命中过，所以该路径的成品级验证只有 2.10 开头那组区域摘要对照。

**单元测试：** 1,063 项，1,051 项通过，9 项跳过，3 项失败。失败的三项是测试里写死的译文与新语料不一致（润色反馈 1 项、发布流程 2 项），与本节改动无关。名场面集对白快照已按新语料用 `author_talk.py` 重新生成，变化只有被改的两句。

### 2.13 繁体本篇带上上一次的组件缓存和镜像（2026-11-20）

语料状态第一次出现时（工作区是新的），台湾本篇＋BEST 要 74.2 秒，而以前构建过的状态只要 47.5 秒。差别来自种子被拒（原因见 2.11：`config/zh-hant/readback-literals.json` 随任何一句改动而变）：

| 台湾本篇阶段 | 无种子、新状态 | 以前构建过的状态 |
|---|---|---|
| 制盘 `iso` | 11.84（无基线，走完整制盘） | 0.20 |
| 组件 `components` | 21.27 | 15.62 |
| 压缩器 `codec` | 3.52 | 0.65 |

两处改动：

1. **镜像基线单独带。** `srwz/edition_incremental.carry_iso_baseline`：组件种子被拒时，仍把上一次已验证的镜像和它的两份报告带进新工作区。`build_iso --incremental` 只在制盘实现、布局策略、源盘、报告、镜像本身的哈希都与记录一致时才用它，并只重写哈希变了的成员，所以这一步与组件定义无关。制盘 11.84 → 0.3 秒。
2. **字典按查过的条目判定。** 每个构建进程把自己向字典查过的条目记在所建工程的 `work/cache/editions/literals-asked/<进程>.jsonl`（`srwz/build_language._note`）。组件阶段全量运行时先清空这些记录，全部通过后写 `complete.json`（`rebuild_zh_font.py`）；带种子时记录随 `work/cache` 一起带到下一个工作区并合并成 `carried.jsonl`。下次构建若字典文件变了，`edition_incremental.literals_answers_unchanged` 比对新旧字典里所有记录过的条目（以及字典除两张表之外的字段），全部相同才当作没变。没有 `complete.json`、旧字典哈希对不上、任何一条答案不同（包括原来没有、现在有了），都按原规则拒绝。台湾本篇整个构建只查 162 个条目。

种子被拒时现在会打印原因：`[original] component caches not carried: <路径> changed`。

顺带修的一个旧问题：带种子进入一个已存在的工作区（A → B → A）时，要覆盖里面只读的小文件（工具链目录里的 git 包索引），`copy_file` 报 Permission denied，构建失败。以前繁体从不带种子，走不到这里。现在遇到只读的旧文件先删再写。

未解决：

- 有一次（上一次构建本身带了种子的情况下）种子被拒，当时还没有打印原因，之后三次同样的链式情况都成功，没能复现。再出现时日志里会有原因。

## 3. 光盘上放了什么

三合一盘沿用简体盘面布局，再写入下面列出的内容。布局器逐字节核对写入范围之外的数据。SP 核对时从简体资源包读取对应字节。

### 3.1 繁体数据放在哪

- 原盘有一个全零的占位文件 `DMY/DMY.BIN`（122,558,928 字节），紧跟在 `DATA/VT1.BIN` 之后。繁体数据写在这里面，光盘目录和文件大小都不变。
- 每个与简体不同的数据文件，整份复制一份繁体版进去。
- 港台两份内容相同的文件只存一份。
- 每种繁体各有一个“补丁文件”，记录开机时要改什么（格式见 4.3）。

| 版本 | DMY 已用 | 台湾版复制的文件数 | 镜像大小 |
| --- | --- | --- | --- |
| 本篇 | 118.7 / 122.6 MB | 18 | 3,799,459,840（不变） |
| BEST | 118.8 / 122.6 MB | 19 | 3,796,187,136（不变） |
| SP | 97.6 / 122.6 MB | 17 | 4,208,431,104（比简体资源包的逻辑盘面多 289,570,816 字节） |

本篇里被复制的文件：战斗台词（SRVC、OP1、OP2）、战斗叠加层（TRICMN）、援护提示（AIDDATA）、名称与属性（COMPDATA）、图鉴（MTVZKN\*、MTV_PRO\*）、教学与问答（NISVDATA）、剧情（STAGE）、特效贴图（VEFF2DX）、界面图集（KVMDATA）、地图（MAPMODEL、MAPNAME）等。BEST 多一个 `HEDBDY/HB.BIN`。

### 3.2 为了只存一份而共用的内容

香港模式下，以下内容沿用台湾版，因此会看到台湾字形（例如 臺地、炮臺）：

- 所有贴图（标题按钮、界面图集、关卡标题、世界地图标题等）。
- 地形名。地形名存在每个地图块里，单独做一份就要再放一份 50 MB 级的地图文件，放不下。
- SP 额外共用：存放在 VT1 里的 24 条页面文字，以及数据链接说明页。

### 3.3 SP 的特殊处理

SP 的 VT1 文件是按“组”连续读取的，一组的长度由下一组的起点决定，所以不能像本篇那样只挪其中一块。做法：

- 整份繁体 VT1（205 MB）追加在镜像末尾，繁体模式下把 VT1 整个重定向过去。
- 繁体的 AIDDATA（79 MB）同样追加在末尾，因为 DMY 放不下。
- 钩子代码放在原程序映像之外的一段内存，可执行文件因此多了一个加载段、变大，被移到镜像末尾。

SP 三合一盘的大小与之前的简繁双语盘相同，因为港台共用这两份大文件。

## 4. 游戏程序的改动

这一节是相对于“简体单语盘的可执行文件”而言。简体单语盘本身已有的改动（中文字库、文字绘制、比例字形等）不在本文范围内。

改动分两类：**固定写在盘上的**（三种语言都一样），和**开机时在内存里做的**（只在繁体模式下发生）。

### 4.1 固定写在盘上的改动

| 改动 | 内容 | 版本 |
| --- | --- | --- |
| 语言钩子代码 | 一段新加的程序和数据，本篇 / BEST 3,696 字节，SP 3,840 字节 | 全部 |
| 开机调用 | 开机流程里的一条 `jal` 指令改为先跳到语言钩子，钩子做完自己的事再调用原函数 | 全部 |
| 标题画面调用 | 标题画面每帧处理函数的那条 `jal` 改为先经过钩子，用来响应 SELECT 打开设置面板 | 全部 |
| 字库缓冲大小 | 一个数值由 0x13B000 改为 1,437,696（4,992 字 × 288 字节），让繁体字库放得下 | 本篇、BEST |
| 新增加载段 | 可执行文件增加一个全零的加载段，用来放钩子代码 | 仅 SP |

钩子放在哪：

| 版本 | 钩子代码位置 | 开机调用点 | 标题调用点 | 运行时缓冲 |
| --- | --- | --- | --- | --- |
| 本篇 | 0x78B640–0x78C4C0（拉丁字形段的空尾） | 0x141010 | 0x155CF8 | 0x789D00 |
| BEST | 0x78BE40–0x78CCC0（同上，整体后移 0x800） | 0x141010 | 0x156098 | 0x78A500 |
| SP | 0x81C600–0x81E000（原程序映像之上的空闲内存） | 0x141B28 | 0x14214C | 在钩子区内 |

- “运行时缓冲”是 84 字节，读写存档卡和拼面板文字时使用。本篇和 BEST 的钩子区已满，所以放在程序段之间一段没人用的空隙里；用内存写入监视跑完整条路线确认过，除开机清零外没有别的写入。
- BEST 的地址是把本篇的地址按周围指令做匹配，在 BEST 程序里找到唯一对应位置得到的：代码位移 0 / +0x3A0 / +0x600，已初始化数据 +0x780，运行时内存 +0x800。

### 4.2 开机钩子做什么

执行时机：手柄端口已打开、文字文件和字库还没开始读取的时候。

1. **决定语言。**
   - 读存档卡 0 号口上的设置文件（见第 5 节）。
   - 开机时按住 SELECT：强制台湾繁体，不改存档卡。
   - 没有卡、没有文件、内容校验不过、语言值超出本盘的语言数：按简体处理。
2. **简体：** 什么都不改，直接进入原流程。
3. **繁体：**
   1. 从 DMY 把该语言的补丁文件读到一块固定的临时内存。
   2. 核对文件标记和校验和。任何一项不对就放弃，游戏留在简体。
   3. 改写内存里的“文件位置表”：把有繁体版的文件指向 DMY（或镜像末尾）里的那一份。
   4. 按补丁记录逐条改写程序内存里的字节（内容见 4.3）。
   5. 把临时内存清零，刷新指令和数据缓存。
4. **所有语言：** 把两个显示选项（数字 0 带点或不带点、对话引号用中文或日文样式）写进绘字程序读取的选项字。

钩子不申请堆内存，简体和繁体两种模式下游戏的堆状态相同。

### 4.3 补丁文件与它改的内容

补丁文件格式（小端）：

- 文件头 32 字节：标记 `ZHTP`、版本、文件位置表行数、记录数、正文字节数、正文校验和。
- 正文：先是若干行（表内偏移、新的起始扇区、扇区数），然后是若干条记录（内存地址、长度、字节）。

记录就是“繁体单语构建的程序”与“简体单语构建的程序”的逐字节差异，另加下面几项专门处理：

| 记录内容 | 作用 | 版本 |
| --- | --- | --- |
| 程序里的文字 | 写在可执行文件里的界面文字、武器分类标签等换成繁体 | 全部 |
| 字库读取指令 | 字库块的位置和长度改成立即数，指向 DMY 里的繁体字库 | 本篇、BEST |
| 缺字回退 | 一对指令改写，启用线性字形查找，支持繁体多出来的字 | 全部 |
| 标题菜单读取指令 | 标题按钮图所在的块改为从 DMY 读 | 本篇、BEST |
| 关卡标题内表 | 117 个偏移统一加一个常数，指向 DMY 里的繁体关卡标题组 | 本篇、BEST |
| 字库缓冲大小 | 繁体模式下才放大 | 仅 SP |

VT1 的块偏移表保持简体的值，因为盘上的 VT1 就是简体那一份。

下表的字节数只计可执行文件记录中的改写数据（回执的 `record_bytes`）。完整 ZHTP 文件还包括头、VMAP 行、记录描述和对齐填充。

| 版本 | 台湾补丁 | 香港补丁 |
| --- | --- | --- |
| 本篇 | 781 条，6,236 字节 | 781 条，6,453 字节 |
| BEST | 783 条，6,320 字节 | 785 条，6,399 字节 |
| SP | 2,249 条，16,273 字节 | 2,831 条，81,790 字节 |

补丁不允许碰的位置：钩子代码区、两个调用点、音乐播放器的挂接点、堆起始字。合盘时逐条检查，碰到就失败。

### 4.4 标题画面的设置面板

- 标题菜单等待输入时按 SELECT 打开。用的是游戏自带的信息框，没有新画界面。
- 三项设置：游戏语言、数字样式、对话引号。上下选行，左右改值，○ 保存到存档卡，× 或 △ 关闭。
- 语言在重新启动游戏后生效；数字样式和对话引号立即生效。
- 面板打开期间标题画面照常播放动画，但收不到按键。
- 提示行的 ○ / × 是游戏自己的按键图标。
- 面板文字按当前显示语言取用，各自用自己的码表编码。香港模式下面板沿用台湾那一套文字。

实现上的两处借用，关闭面板时都会还原：

- 信息框只能显示消息表里的条目，钩子临时把一个消息槽的文字指针和属性换成自己的。
- 首次保存要在存档卡上建目录，钩子借用程序里现成的存档图标和图标描述，让主机的存档管理界面把它显示成正常的游戏数据。

## 6. 合盘时的自动校验

合盘脚本在目标文件系统上克隆出临时 ISO，所有检查通过后才替换该版的成品和回执。检查失败会删除临时文件，保留上一份已验证成品。三个版本分别发布。

- 钩子的两个调用点和字库缓冲字，改写前的原值必须与预期一致。
- 钩子代码区在改写前必须全零；汇编结果不能超出钩子区。
- 把补丁在简体程序上重放一遍，结果必须等于繁体程序。
- 没有补丁记录落在禁止范围内。
- 每个不同的数据文件都必须能通过文件位置表重定向；VT1 里出现没有专门处理的差异块就失败。
- DMY 写入范围必须位于占位文件内，原区域必须全零。两份 ZHTP 补丁按各自的 LBA 和完整文件长度从临时成品读回，逐字节对照合盘器生成的内容。
- 写入范围之外，成品与简体镜像逐字节相同。

## 8. 已知限制

- 香港模式下贴图和地形名是台湾字形（见 3.2）。
- 改名画面的选字表在繁体模式下没有处理。
- 繁体攻略问答是机器初稿。
- 没有实机看过：香港模式下剧情和战斗台词的通读、BEST 独有的关卡和台词、SP 繁体的关卡流程、音乐包在三合一盘上的兼容性。
- 构建只在 macOS 上跑过。Windows 上还有三处障碍：`build_editions.py` 用了 `fcntl`，SP 基线步骤用符号链接，仓库里的 `rom` 是符号链接。
- 语言工具使用 `SRWZ_LANGUAGE_PYTHON` 指定的 Python。SP 的贴图和预览构建使用 NumPy 和 Pillow。
- 三语发布使用 schema 7。每版先核对三种语言的候选批次、合盘回执、宽屏回执，再冻结最终盘。命令见 [统一构建说明](BUILD_EDITIONS.md)。
