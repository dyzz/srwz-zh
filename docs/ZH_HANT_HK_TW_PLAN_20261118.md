# 繁体港台区分方案（2026-11-18）

## 1. 用户决定

- 区分到：字形 + 常用词 + 作品名。
- 香港版从台湾版派生：自动转换 + 用词表 + 逐条手改覆盖。台湾版改动后，香港版自动重派；手改过的条目标为待复核。
- 贴图港台共用一套，沿用现有繁体（台湾字形）。

## 2. 现状（实测）

- 现有繁体语料是 s2tw 字形 + 大陆用词。bootstrap 只换了 5 个词：感測器 / 螢幕 / 訊號 / 資料 / 遠距攻擊。
  - 例：高達 1,548 处、信息 277、程序 32、網絡 10、軟件 5、視頻 7。
  - 所以台湾版本身也要做一轮用词修订，不能直接把现有繁体当成台湾版。
- 台→港字形（OpenCC tw2t+t2hk，在 13.9 万条字符串上实测）：
  - 37 组字，例：說→説 8,590、裡→裏 4,490、著→着 3,265、臺→台 1,011、衛→衞 893、脫→脱 399。
  - 涉及 17,371 条（12%），需要新增字形 36 个。
  - OpenCC 的部分映射不可直接用，要人工挑选：群→羣、參→蔘、梁→樑、峰→峯 等。
- OpenCC s2twp 的词表不可用。例：梅爾·比特→梅爾·位元，加納利→迦納利，的士兵→計程車兵。用词一律用自建表。
- 字库：繁体码表 3,754 / 4,992 字，加香港字形放得下。港台共用一套字库（两地字形取并集），所以字库不分港台，只有文本分。
- 贴图中含有港台不同字形的只有少数几处，香港版沿用台湾字形：
  - 說（按鍵說明 / 項目說明标题、部分帮助图）
  - 衛（世界地图标题）
  - 啟（关卡标题）
  - 群（编队图集）
- 光盘空间（繁体存放区 DMY，116.9 MB）：

  | 盘 | 已用 | 剩余 | 主要占用 |
  | --- | --- | --- | --- |
  | 本篇 | 104.8 MB | 12 MB | MAPMODEL 52.6、VEFF2DX 35.3、STAGE 3.7、SRVC 3.2、MTV_PROP 2.1 |
  | SP | 86.6 MB | 30 MB | |

  - 香港版只需复制"文本有差异的成员"，估计本篇约 10–11 MB，很紧。BEST 待测。
  - 贴图成员（MAPMODEL / VEFF2DX / KVMDATA …）共用台湾版的副本，不再复制。
  - 如果某个大成员只因为文本里的一两个字形不同而要整体复制（例如 MAPMODEL 里的地形名），就让该成员沿用台湾字形，并在报告里列出。

## 3. 里程碑

- **H0 用词表**：作品名 + 常用词，台湾 / 香港各一栏。每组规则有三种：
  - 全局替换；
  - 按日文绑定（例：程序 只替换日文是 プログラム 的条目）；
  - 例外清单。
  - 候选表：`work/analysis/zh-hk-tw-20261118/candidates.md`，由 `term_candidates.py` 生成。**需要用户确认。**
- **H1 台湾版用词修订**：按用词表修改 `corpus/*-zh-hant`。
  - draft 条目由 bootstrap 规则重派；edited / reviewed 条目逐条写入。
  - 规则文件和改动清单都留档，满足"有来源依据"的要求。
  - 替换后长度不变的词（鋼彈 / 高達 等）不影响排版；长度变化的词要过版式门槛。
- **H2 香港派生**：
  - 新工具 `tools/zh_hant/derive_hk.py`。处理顺序：台湾语料 → 字形表（人工挑选的子集）→ 港台用词表（按日文绑定）→ 覆盖表（`corpus/zh-hant-hk-overrides/`）→ 生成香港树。
  - 生成的树只作为构建输入，不提交。
  - 同步检查：台湾条目哈希变化后，对应的覆盖条目标为 stale。
- **H3 香港单语构建**：本篇、BEST、SP 各一个克隆。共用繁体码表 + 字库，香港字形追加到码表。
  - 贴图链与台湾版逐字节相同（校验）。
- **H4 三语组装**：
  - DMY 再放一份香港补丁文件，以及与台湾版不同的文本成员。
  - lang_hook：语言值 0 / 1 / 2，按值选补丁文件。
  - 标题设置面板：语言一行在 简体 / 繁體（台灣）/ 繁體（香港）三项间切换。
  - LANG.BIN 值 2；开机按住 SELECT 仍强制台湾版。
  - 简体、台湾两种模式与 H1 后的双语盘逐字节一致。
- **H5 运行验证**（ARMSX2）：三种语言的启动和切换、存档互通、音乐包、空间余量；本篇、BEST、SP 都要测。

## 5. 构建方式改造（2026-11-19，用户："不要克隆，当前目录要允许多语言语料"）

- 原来的做法：每种语言把工程 `cp -cR` 一份到 `build/zh-hant/project-*`，在副本里换语料再跑一遍流水线。只能在 macOS 上跑，缓存跟着副本一起被删。
- 现在的做法：语言是 `build_editions.py` 的参数，在当前目录直接构建。
  - `build_editions.py --language zh-hant-tw|zh-hant-hk`。不带参数就是简体，行为和产物不变。
  - 冻结输入时生成该语言的"输入视图"（`srwz/release_inputs.py` 的 `freeze_inputs(language=…)`，`srwz/language.py`，`tools/zh_hant/language_view.py`）。视图就是原来 `prepare_tc` / `menu_codebook` / SP 的 `sp_prepare` 做的事，只是作用在冻结快照上；之后的流水线一行没改。
  - 每种语言有自己的工作区、缓存目录、构建锁、回执和输出：`manifests/editions/<版本>/candidate-<语言>.json`，`build/iso/test/integrated-<版本>-<语言>.iso`。
  - 压缩缓存、版式缓存在仓库的 `work/cache` 下，三种语言共用。
  - 视图有缓存：输入和所依赖的本篇构建都没变时，直接用上次的视图。
  - SP 的繁体视图只能单独构建（它带 SP 专用的输入）；继承文本取自同语言的本篇构建，所以要先建本篇。
- 一条命令：`python3 tools/build_multilang.py`。只出三合一盘（用户 2026-11-19："我们就只 build 3合1"）：没有双语盘或单语盘的选项，`integrated-*` 单语镜像只是中间产物。
  - 第一阶段并行：本篇三种语言 + SP 简体。
  - 第二阶段并行：SP 台湾 + SP 香港。
  - 合盘：`build/iso/test/multilang-original.iso`、`multilang-sp.iso`。
  - 繁体视图要用 opencc：当前解释器没有时，用环境变量 `SRWZ_LANGUAGE_PYTHON` 指定一个有 opencc 的 Python。
- 构建不再自动重画贴图或扩码表。过期时构建停下并提示：
  - 贴图：`tools/zh_hant/build_dual.py --author-textures`
  - 码表：`tools/zh_hant/build_dual.py --update-codebook`
  - 关卡标题：`tools/zh_hant/author_stage_titles.py`
  - `build_dual.py` 现在只负责这些作图步骤要用的繁体工程（`build/zh-hant/project-tc`，用普通复制，不依赖 APFS）。这三条作图命令改造后没有实际跑过。
- 验证（改造前的输入）：
  - 本篇 简体 7917b9ce、台湾 d714aa00、香港 900ea24b；SP 简体 3034c4a8、台湾 0e30e338、香港 42bd04d1：都与克隆方式的产物逐字节相同。
  - 合盘：本篇 2a35c28b、SP 57ec4fd2，与昨晚的三语盘逐字节相同。
  - 单元测试 1,040 项通过（跳过 9）。
- 耗时：两张三合一盘全部重建 301 秒（第一阶段 101 秒，第二阶段 190 秒，合盘 9 秒）。克隆方式下只 SP 的两个繁体版本就要约 19 分钟。
- 还没做：
  - `migrate_compdata` 之后 `return_compdata_strings` 把 COMPDATA 整份再压一遍（各 64 秒，缓存未命中时）。
  - Windows：`build_editions.py` 用了 `fcntl`；`sp_tc_baseline.py` 用符号链接指向答案目录；仓库里的 `rom` 是符号链接。
  - 构建时仍需要 opencc（转换工具脚本里的常量和 SP 配置）。

## 6. BEST 三合一（2026-11-19，用户："BEST 也要做"）

- 构建：`build_editions.py --editions original,best --language <语言>`。BEST 用同一语言的本篇做文本前端，和简体一样一次构建出两版；不需要 BEST 专用的视图。
- 钩子地址（`tools/zh_hant/editions.py` 的 `BEST`）：BEST 和本篇是同一套引擎，只有小幅位移。
  - 查法：把本篇的每个地址，按周围指令做掩码匹配（跳转目标和立即数不参与比较），在构建出的 BEST 可执行文件里找到唯一对应位置；数据地址取匹配到的代码里的操作数。
  - 结果：代码位移 0 / +0x3A0 / +0x600，已初始化数据 +0x780（消息属性表 +0x830），运行时内存 +0x800。
