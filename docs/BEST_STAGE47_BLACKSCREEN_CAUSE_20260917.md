# The Best 第 47 话标题后黑屏：根因定位

2026-09-17。状态：**根因已定位；随后按用户要求扩展静态审计并进行 LRPS2 诊断对照。正式生产代码及 current ISO 未修改**。

第一轮仅定位原因时，沿用用户已经实测的对照：stock JP Best、stock JP Original、汉化 current-original 正常；汉化 current-best 在第 47 话标题后永久黑屏。未重新启动模拟器、加载存档或执行 R1+START 流程。仅进行 ISO 二进制分析、构建函数复算，以及只读检查同目录已有黑屏快照。

## 结论

“我们的去向”在游戏中显示为第 47 话，对应 `DATA/STAGE.BIN` 内部块 **111 / stg_083.bin**。不要将显示话数 47 直接当成 STAGE 块号；流程图内部标题编号也不等于玩家路线中的话数。

Best 构建器对 STAGE 111、150 启用 `shared_text_tail`：把首个文本地址至块末尾全部划为可复制的中文文本区。但块末尾还包含 **10 项地图事件分发跳转表**。复制 Original 的中文尾部时，该表也被一起复制，既保留了 Original 的表位置，又保留了 Original 的函数地址；Best 的分发代码却仍按 Best 原生位置读表。

这导致进入地图的事件 8 跳到错误地址，足以解释“开场对白和标题正常，进入地图时黑屏”的现象。问题发生在 Best 迁移后端，不是通过改对白、字体或按键时序可以消除的错误。

## 第 47 话的具体错误

下表偏移均相对于解压后的 STAGE 111 块；地址为 EE 虚拟地址。

| 项目 | JP Original / 汉化 Original | JP Best | 汉化 current-best |
|---|---|---|---|
| STAGE 加载基址 | `0x7566F0` | `0x756EF0` | `0x756EF0` |
| 分发器读取表的位置 | `+0x21160` | `+0x21150` | `+0x21150` |
| 有效的表实际放置位置 | `+0x21160` | `+0x21150` | 复制了 Original 表到 `+0x21160` |
| 分发代码读取的事件 8 目标 | `0x756E40` | **`0x757640`** | **`0x756DE0`** |

Best 原生表地址为 `0x778040`，10 个目标应为：

```text
00757648 00757648 007575C0 007575D0 007575E0
00757600 00757610 00757630 00757640 00757620
```

当前汉化 Best 在同一地址实际读到：

```text
00000000 00000000 00000000 00000000 00756E48
00756E48 00756DC0 00756DD0 00756DE0 00756E00
```

这里同时有两个问题：表错位 `0x10` 字节，以及表项仍然是 Original 地址、缺少 Best 的重定位。只给旧表项加 `0x800`，或者只移动表的位置，都不足以同时解决二者。

Best 主程序 `0x141A00` 写入事件号 8，调用 `0x1766E0`。后者通过全局 `0x595A78` 调用本关分发器 `0x757580`。分发器在 `0x7575A4` / `0x7575A8` 构造表地址，取出 `table[event]`，在 `0x7575B8` 执行 `jr v1`。

- 正常事件 8：跳到 `0x757640`，继续调用本关地图初始化处理。
- 当前汉化 Best：跳到 `0x756DE0`，低于本关加载基址 `0x756EF0`，已经越出本关代码区域。
- 既有黑屏快照中，该错误目标处存放的是文本样式字节，不能作为正确的地图事件处理函数。

## 源码中的责任位置

`config/editions/best/source-layout.json` 的 `stage_layouts.111` 和 `.150` 均配置 `shared_text_tail: true`。

`tools/srwz/best_build.py:BestCompiler.compile_stage`：

1. 第 194–197 行从首个文本开始，把整个余下块划为文本 `regions` 和 `mask`。
2. 第 199 行将 Original 整段尾部复制到 Best 临时输入。
3. 第 211–212 行再次用编译后的 Original 中文整段覆盖输出。
4. 第 214–216 行只修正尾部之前的完整 32 位地址，不处理尾部函数表，也不处理分发器里的 `lui/addiu` 表地址构造。
5. 第 228–230 行的别名扫描跳过整个 `mask`，尾部函数表继续被排除。
6. 第 241 行开始的 `verify_stage_texts` 校验解析文本、说话人和编码控制内容，没有校验地图事件跳转表。

用当前源代码的 `compile_stage()`，以四张 ISO 中直接提取的原盘和中文块作为输入，复算出的 STAGE 111、150 与故障 current-best 中的对应块**逐字节完全一致**。因此这不是仅存在于源码推测中的可能性，也不是单个 ISO 偶发写盘损坏；当前构建逻辑可以确定地产生这份错误数据。

进一步追溯发现，这个处理在早期实验工具 `tools/build_best_candidate.py:port_stage()` 中已经存在，随 `9d0d8ca`（2026-09-05）保留入库；`3761b7a`（2026-09-07，`feat: 构建并验证同批 Original 与 BEST 镜像`）将相同处理带进当前正式 Best 后端。当前源码仍保留此逻辑。

## 修复边界

需要为尾部的非文本结构建立独立边界与重定位规则，协调函数表位置、Best 函数目标和分发器中的表地址构造，不能继续把整段尾部视为文本。

若保留现有中文尾部布局，可将事件表保留在 Original 布局位置，但必须写入经过原生 Best 核对的全部十个函数地址，并同步更新 Best 分发器 `lui/addiu` 指向该表；还需核对中文末尾与表的边界。不能简单在 Best 旧表位置直接覆盖，因为中文尾部可能已经占用那里。另一实现选择是按 Best 原生表边界重新分配中文文本。两种方案都应校验全部分支目标，而不是只补事件 8。

构建和独立 ISO 回读应增加此非文本结构检查，覆盖 111、150，并能拒绝表地址未更新、表项保留 Original 地址、文本覆盖表三类错误。运行复核按用户安排进行。本轮未实施修复、未重建或替换 current ISO、未提交或推送。

## 后续：当时为什么这样调整

当时目标是复用同批 Original 前端已经完成的中文排版、重排指针和字码分配。Best 原生文本池与 Original 不完全相同，111、150 不能仅把所有文本指针加 `0x800` 后直接套用：

- STAGE 111：Best 官方把 `プレンゼント` 改成 `プレゼント`，文本缩短；末尾分发表从 `+0x21160` 移到 `+0x21150`。
- STAGE 150：Best 将固定主角姓名 `「ランド！」` 改成动态姓名 `「$n！」`，并存在文本布局变化；末尾分发表从 `+0x19D60` 移到 `+0x19D40`。

早期代码注释明确写着 `Best shrank native strings; the Chinese pool stays in its already validated Original allocation layout`，随后又把名称标签尾部划进同一区域。设计目的有实际需求：保持一份中文布局，避免为 Best 再独立排一次文本。

本轮临时关闭 `shared_text_tail` 后复算，普通迁移路径确实会因原生布局不匹配拒绝构建：111 在 `+0x8F00`，150 在 `+0x1300` 报 `unknown native field overlap`。这证明不能简单删除配置当成修复。

错误是**把“沿用中文文字布局”实现成“复制至整个块末尾”**，误认为尾部全部归文字所有。文本回读通过并不能证明附带的函数表正确；该非文本结构缺少独立所有权边界和回归检查。
