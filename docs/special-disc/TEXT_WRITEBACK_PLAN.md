日期：2026-09-19。当前五份译稿的写回、布局和 ISO 静态校验已完成，详见 [全量文本候选](FULL_TEXT_CANDIDATE.md)。下文保留实施前的依赖与发布规划。WB-01～05 已具备实际产出；WB-06 的当前译稿范围完成，图鉴／Q&A 新译缺口另计；WB-07 的候选合成完成，正式运行／审校门仍待关闭。
本计划承接 [目录整理](LAYOUT.md) 和 [现状盘点](STATUS.md)，目标是把现有译稿逐项写入可验证的 SP 开发镜像，再补齐发布条件。

## 1. 目标与当前基线

近期目标：先生成一话剧情和一关挑战可验收的中文候选，再推广到剧情／挑战全量、新增战斗字幕和全部范围内的文字面。
开发候选可以显式使用 draft，但不把草稿改标为已审。发布必须另行满足审校、覆盖和运行验收条件。

当前基线：

- 预览镜像：`build/iso/special-disc/preview/sp-image-preview.iso`，SHA-256 `51a819a426ce049a0ee6ae5c696bb48290445cd8322bf192e2cc45271d1e4a8b`。
- 已有 11 个组件；剧情 `stage-dialogue/` 只有试排报告，没有 `DATA/STAGE.BIN`。
- 5 份专有语料合计 8,629 条，均为 draft；主篇复用译文另计。
- 现有报告的 8,613 条匹配／无换行拒绝不包含中文编码、文本池重排、指针修复或逐块重压验证。
- 目前 SRVC 写回器只读取本篇 `reviewed` 语料，未消费 SP 的 `battle-lines.json`。
- 现有装配器遇到缺失组件报告会跳过；完整文本构建必须改为按所选范围检查必需组件，不允许缺少剧情组件仍报全量成功。

本节“当前基线”保留制定计划时的状态；后续实施结果以首批文本候选页为准。

## 3. 统一的输入与准入规则

### 3.1 译文绑定

建议生成显式绑定表，每个目标至少记录：语料文件与 entry ID、原盘身份、member、chunk／原生记录 ID、kind、原文哈希、指针字段、真实存储范围、采用译文来源和布局 profile。

绑定顺序：

1. SP 条目的稳定位置 ID 与原文哈希同时吻合，采用该条译文。
2. 该位置没有 SP 译稿时，查同领域、本篇已审的原文哈希候选。
3. 本篇有多个不同答案时，依照字段、说话人或上下文选择，并留下选择依据；不能按遍历顺序取第一条。
4. 原文身份不符、重复目标译文冲突或无法唯一定位时，停止该候选构建并列出具体记录。

本次重新核对：所谓 52 次冲突来自 **51 个原文哈希组、108 条记录**。其中既有“军机库／军用机库”这类术语差异，也有不同说话人的短句标点差异。先按位置保留合理差异，需统一的项目交给审校；不要为了哈希索引而强行合并全部译文。

### 3.2 开发与发布

拟提供显式开发选项（`--allow-draft`，已在首批关卡写回器实现），允许现有初稿进入指定范围候选。输出报告必须保留使用了哪些 draft；不能通过改 `editorial_status` 绕过审稿。

发布模式只接受既定已审状态，要求范围内所有应汉化落点完成写入和回读。保留英文、数字、开发字符串或明确排除图片需有分类依据；不以“搜索不到假名”为唯一覆盖检查。

### 3.3 编码、字库与容量

- **沿用本篇同一份码表与字库生成流程，不另建 SP 码表。** SP 现有 `encoding_tables()` 已读取本篇映射和既有别名／兼容规则；新增字符追加到共享分配表，旧码位保持稳定，保证本篇存档与 SP 数据链接使用同一套编码。
- 当前缺 `乒乓捂捆掮撵焕篱纽耷耸胺踹钏` 14 字，共享分配表仍有 **75 个普通宽度候选位**，数量足够；这批优先走本篇普通候选分配流程，无需为它们进一步开放特殊区间。特殊位置继续遵循本篇的适用场景规则。
- 本篇字宽测量范围补丁已进入当前 SP 镜像：主程序文件偏移 `0x3B0E0`、`0x168A1C` 的指令均为 `9f820134`，即把测量上界从 `0x889F` 改为 `0x829F`，与绘制分类一致。此项属于已移植基础，后续复验保留，不作为待重新设计的难题。
- 字库压缩空间同样已有迁移实现。当前 629,099 字节压缩流按 16 字节对齐分配 629,104 字节，“余 5 字节”只是本次分配后的对齐余量，**不是整个字库可扩展空间只剩 5 字节**。
- `install_font.py` 已按新压缩大小动态计算 `needed` 和 `borrow`，移动音频块并更新两项 VT1 表。原盘此前可借零尾实测 356,850 字节，当前用了 29,760 字节，尚有 327,090 字节。新增字后沿用该逻辑重建并核对哈希／容量即可；最终增长量以实际重压结果为准，无需预先设计另一套扩容方案。
- 码表、字形生成和 SP 字库组件同步刷新并绑定输入哈希，防止新码表配旧字库；缺字集合按本次实际采用的译文重新计算。
- 两字节取字面使用项目的可见空格转换规则，保留英文与数字。分别验证 `Orange` 的 13／9 字节问题和 `Keep On Movin'` 的 29／23 字节问题；字宽调整不等于存储字节减少。
- 优先使用已证明可用的原槽／零尾或具备引用契约的池重排。不得静默截断、吞掉控制码或为过容量门改掉已要求保留的英文。
- 如修改共享字体／解析基础，执行相关 Original／BEST 回归。区分旧映射和行为兼容，与因增加字形而预期变化的字库字节；按实际影响更新锁，不承诺新增共享字形后两版 ISO 仍逐字节相同。

## 4. STAGE 的写回设计

### 4.1 先建立原生结构清单

以 `SLPS_259.20`、HB 和原盘成员锁为身份依据，从当前系统组件的 STAGE 开始，保证此前 flow 和滚动播报改动保留。
当前导出适配使用 SD base `0x8045F0`、HB 表起点 `0x5170`；这些必须进入版本明确的契约，不能照搬本篇地址。

实施前 `sd_stage_module()` 通过替换本篇解析器源码插入 SD 地址与 `0x63` 记录。现已把这些变成显式参数／SD 适配层，并补对应解析验证，避免构建依赖源代码中的某行文本。

每块清单至少包含：压缩边界、解压大小、事件／分派表、已识别指针字段、每个真实存储串的起止与终止符、说话人前缀、正文、条件、小队名、共享／中间引用及未知数据范围。

### 4.2 只在所有权明确的范围内重排

1. 用原始字节解码结果的 `consumed`／`end` 判断存储长度，不能用“重新编码日文的长度”推算原始区间。
2. 对“说话人＋换行＋正文”分别绑定显示文字，再按原记录结构组装；保留控制码、变量、前缀分隔和终止符。
3. 当前解析末尾之后的胜败条件等数据不能视作空闲。已有调查记录的 7,126 个非零字节先原位保护；识别了全部引用与结构后，才允许纳入移动范围。
4. 共享同一串、指向串中间的引用分别登记。不同位置需要不同译文时，只有在相应引用可独立改写且容量允许时才拆串；否则作为明确冲突处理。
5. 对所有拟移动目标审计引用。无法归类的同值地址不是自动可改写指针：保持其目标原位，或完成类型确认后再移动；若无法安全分配则失败。
6. 重排后重写全部已登记的引用，验证不悬空、不越界、不重叠；未拥有的代码、事件表、参数与未知段保持原字节。
7. 逐块编码、重压、再次解码与解析。第一阶段保持 HB 区间、文件长度和解压大小不变；确有不足再单独设计 STAGE 档案内重排，不在首次 canary 中同时扩大变更。

“文本变短约 25%”仅是可行性线索，不作为逐块容量证明；`overflow=[]` 必须来自真正执行过的容量检查。

## 5. 成员合成与最终布局

保留现有组件链作基线，新增内容按成员前像哈希串接；最后一个组件必须消费同成员上一步的实际结果。

| 成员 | 合成责任 |
| --- | --- |
| STAGE | 现有 flow → 现有 system-text → 同一次关卡写回处理对白／说话人／条件／小队名 → 补 SD flow 内容；各步保留之前改动 |
| COMPDATA | 本篇复用 → 系统及 menu 初稿 → 话名与剩余字段；最终一次按实际完整文本池验证容量 |
| SRVC | 从锁定原盘，用合并后的本篇已审＋SP 候选译文重建一次；避免给旧中文再按日文扫描打补丁 |
| NISVDATA／图鉴 | 已有迁移基础上补差异，或从锁定原盘一次合并重建；必须明确选一种并绑定实际起点 |
| VT1 | 新字库／音频迁移、40／50 块文字、图片内容先按 chunk 身份收齐，再计算最终布局和偏移表 |
| HSFC | 节点简介与既有标题图片一起合成，最终统一计算压缩布局 |
| 主程序 | 系统文字与补丁、各归档最终表项按区间合并；不同组件覆盖同一范围时检查前像与预期，禁止最后一份完整主程序覆盖前面成果 |

当前图片装配器含原盘压缩流绝对偏移。VT1／HSFC 新文字若触发布局移动，这些旧偏移不能继续直接使用。计划改为 **chunk ID＋块内 TIM2／picture 身份** 定位，检查来源锁，再做最终重排；每份偏移表只有一个最终布局计算者。

组件报告增加 `status`／实际执行的检查、所用语料与码表／字库哈希、`base_files`、`original_files`、`files`、写入／保留／未解决落点及容量结果。试排报告与可装配组件区分，缺组件、旧输入或未执行检查不能自动变成通过。

新文本候选使用规划中的独立目录 `work/build/special-disc/text-candidate/`、`build/iso/special-disc/text-candidate/`，先保留当前图片预览作为基线。组件稳定后再接入正式 current 入口。本计划不创建空产物目录或伪造构建报告。

## 7. 验证与提交边界

静态验证至少覆盖：原文身份、条目与目标唯一性、控制码／变量保留、真实存储边界、共享／中间引用、未知段保护、指针完整性、逐块压缩与解压预算、HB／事件结构、组件前像链以及最终镜像内容回读。

新增测试针对容易产生真实损坏的场景：带说话人前缀的串、未解析条件尾部、共享串分歧、中间引用、错原盘／错前像、缺字、压缩后超槽位、缺必需组件、字库／码表不配套，以及 VT1／HSFC 文字与图片共同重排。不要只测试“写进去后能读出同一字符串”。

运行证据按新候选记录，覆盖进入／返回、剧情／挑战事件、回看、保存／读取和新增音频布局相关播放。LRPS2 通过与 PCSX2／手工通过分开登记；旧图片预览截图不能作为新剧情候选验收。

建议按功能边界提交：绑定／解析契约；字库及相关锁；STAGE 写回与结构验证；SRVC 新句接入；flow／固定格／旁白；资料库补漏；最终装配与验收摘要。译稿审校另成提交，保留现有未提交工作归属。ISO、原盘成员、作者工作包和运行缓存继续本地保存。

本次建议下一步开始 **WB-01＋WB-03 的只读结构清单和写回基础**，同时以 WB-02 的实际字库容量为首批镜像依赖。首个里程碑仍是“生成可回读、可运行的两关候选”，不是再出一份匹配率报告。
